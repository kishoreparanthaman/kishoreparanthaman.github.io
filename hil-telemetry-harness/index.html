HIL Telemetry Harness

A hardware-in-the-loop pipeline that connects a real six-joint robot arm to GPU policy inference, measures the latency of every hop, and tests whether a busy GPU disturbs the arm's control timing.

The question

When a GPU is busy running policy inference, does the timing of the robot arm's control link get worse?

The answer

No, not measurably. The arm's 15 Hz control tick held 66.67 ms at the 99th percentile with the GPU idle, running a transformer policy, or running a diffusion policy back to back at the GPU's power limit. What did disturb the loop was CPU contention: with every CPU thread saturated, the actuator process woke up to 2.1 ms late.

The problem

A learned robot policy runs on a GPU. One call takes anywhere from 2 ms to 300 ms depending on the model, and the time varies from call to call. The motors, on the other hand, need a new target on a fixed beat. If the control loop waits for inference, every variation in inference time becomes variation in the motion.

The usual design answer is to decouple the two. The policy runs asynchronously and returns a chunk of future actions. A separate actuator loop plays the newest chunk out at a fixed rate and never waits for the GPU. The claim this design rests on is that actuator timing is independent of inference load. That claim is usually assumed. This project builds the pipeline, measures it hop by hop, and tests the claim on hardware.

Success was defined as measurement and explanation: a latency distribution for every hop, with a stated cause for the shape of each one.

What the project is not

  • It is not a manipulation demo. The arm does not pick anything up.
  • It makes no sim-to-real claim. The two learned policies were pretrained on other robots and tasks. They are used as realistic inference load and never drive the arm.
  • There is no physical camera. A simulated twin of the arm renders the frames the policies see.
  • Everything runs on one laptop, so the results describe one host sharing its CPU and GPU between simulator, inference server and actuator.

Six design decisions carry the result:

  • Stale data is never queued. The receive buffer has a fixed size and overwrites its oldest frame. The consumer always takes the newest. A slow consumer loses frames; it never falls behind.
  • The policy and the actuator run on separate clocks. The policy sends action chunks over UDP whenever it finishes. The actuator resamples the newest chunk onto its own tick grid, so a late chunk changes what is commanded, never when.
  • A safety filter is the last step before the arm. Every chunk is checked against joint limits, speed limits, the tabletop and the base, whatever produced it.
  • Every hop is timestamped on one monotonic clock. All processes share a host, so one-way latency is measured directly with no round-trip estimate.
  • A no-ML policy goes through the same serving path as the learned ones. That separates the cost of serving from the cost of the model.
  • Every hardware step was rehearsed on a software mock of the arm, later calibrated from the real arm's measured servo response.

Formal measurements follow a fixed benchmark protocol: GPU core and memory clocks locked, CPU governor set to performance. A script checks the state and the formal runs refuse to start without it. The reason for the protocol came out of the first phase.

Phase 1

Transport baseline, before any model or hardware

The simulator sends frames through the UDP link to a receiver that discards them. This is the control condition for everything later. The target was under 2 ms at p99 for pure software overhead (serialize, send, deserialize).

The target was met by about ten times. Two tails needed explaining, and neither had the usual cause.

The UDP latency had two modes

About 25 µs or about 120 µs. Garbage collection, socket buffers and the Python interpreter lock were each ruled out. Pinning the receiver to each core type settled it: the slow mode is the receiver thread being woken from sleep. On the low-power cores every packet was slow; a busy-polling receiver on performance cores had none (p99 161 → 35 µs).

Rendering had a 4 ms tail

At 200 Hz the GPU is idle about 97% of the time, so the driver drops it to its lowest power state between frames. Each frame then pays to re-clock. Locking the core clock alone did not help, because the driver still parked the memory clock. Locking both took render p99 from 3.6 to 0.44 ms.

This mattered beyond Phase 1. The simulator and the policies share one GPU. Without locked clocks, starting inference would have sped up the simulator by keeping the GPU awake, and the load generator would have been coupled to the system under test. The same effect exists on the CPU: paced calls ran three times slower than back-to-back calls because the processor held an under-used core at low frequency.

Phase 2

Inference: three policies through one serving path

Both learned models were exported to ONNX, compiled to TensorRT, validated numerically against the original PyTorch model, and served by Triton. Before either was timed, eight predictions were written down from an analytic cost model (operations and bytes moved per call against the GPU's compute and memory-bandwidth ceilings).

The two misses were the informative part. The cost model counted the model's weights but not its activations: ACT's image feature maps add about 110 MB of memory traffic per call, and its 385 kernels are too short to fill the GPU at batch size one. For Diffusion, the model described the GPU kernels correctly but not the system: a chain of 100 short calls pays a per-call host cost 100 times.

  • ACT was slow because of transport. Of the first version's 14.4 ms, about 2 ms was inference. The rest was converting and moving a 3.7 MB image. Sending the 16.5 KB JPEG and decoding it on the GPU made the loop 2.7 times faster with the same model.
  • Diffusion's extra cost was located. Moving the denoising loop into the server saved only 0.13 ms per step, so the network call was not the cause. The server's per-request path was. Running the whole loop as one GPU graph outside Triton reached 2.50 ms per step against a GPU-only floor of 2.43. That path was measured but not served.
  • 8-bit quantization was rejected on measured quality. It was as fast as predicted, but ACT's joint outputs moved by 2.6–3.8° at p99 (half precision: 0.05°), and Diffusion's output drifted about four times its own run-to-run spread. Half precision was kept.
  • Selection: ACT at half precision. One call fits inside about one 5 ms frame and returns 100 future actions. Diffusion at 100 steps acts on an observation roughly half a second old.
Phase 3

The real arm: safety layer, fault injection and the independence test

What the hardware dictated

  • The control rate is 15 Hz, set by the arm. The arm's controller sends no acknowledgement for a move command and cannot answer a read for about 43 ms afterwards. A read sent 20 ms after a command was lost in 2–13 of 40 trials; at 35 ms, 0 of 160. A loop that reads every tick therefore needs at least 53 ms. The actuation path is about ten times slower than the selected policy's inference.
  • The kinematic model matches the firmware to 0.14 mm.
  • Three different joint-limit tables exist for this arm (published, firmware, Python library). The safety limits take the tightest value per joint.
  • Speed limits are measured. Every joint follows 40°/s and saturates near 55–60°/s, so the limits were lowered from the initial guess to 40°/s (large joints) and 50°/s (wrist).

The safety layer

The filter checks every chunk in a fixed order: non-finite values or a malformed duration reject the chunk and the arm holds; joint limits are clipped; a jump of more than 30° from the current command is clipped; speed is rate-limited; and the chunk is cut off at the first target that would bring any link within 4 cm of the table. The actuator adds a 250 ms watchdog, a tracking check, servo temperature and voltage monitoring, and a stop on any serial error.

Faults were injected into a live command stream on the real arm, in one 63-second run:

The filter also shows why the learned policies never drove the arm. At the measured speed limits it had to correct 97.4% of ACT's chunks and 52.2% of Diffusion's, against 1.7% for Model A. That is expected for policies trained on other robots.

The independence experiment

The arm did the same thing in every run: a slow ±5° sway of the base joint under the full actuator and safety stack. Only the load changed. Six conditions, two 2-minute runs each, in shuffled order, under the benchmark protocol. Every serial transaction and every inference call was logged on the same clock.

Serial read: time from writing a joint-angle query to parsing the reply. Wake lateness: how late the actuator loop woke after its deadline. Two runs pooled per condition; about 21,000 queries in total, one failed mid-run.
  • GPU load made no measurable difference. Each loaded condition differs from the baseline by less than two runs of the same condition differ from each other (distribution distance 0.05–0.11 against 0.14 between repeats).
  • No coupling inside a run either. A read sent while an inference call was in flight took the same time as one sent while the GPU was idle (16.8 against 16.8 ms for Diffusion).
  • The spread in read time comes from the arm. From tick to tick it steps down 3.6 ms or up 6.4 ms, the same two steps in all 12 runs. Host scheduling noise would not produce that. The exact mechanism inside the controller was not identified.
  • CPU contention is what the actuator feels. Under condition e the loop woke up to 2.1 ms late and the tick stretched by the same amount. The serial read itself did not change and no reads were lost.
  • Pinning without isolating the core made things worse (110 µs against 1.2 µs), because the scheduler could no longer move the actuator away from a busy core.

Closed loop on the arm

With the twin as the camera, Model A drove the real arm to hover over a moving virtual target through the full pipeline, while ACT ran on the same frames as load. The loop behaved as the calibrated mock predicted.

Both real runs ended after 13–14 s. The supply voltage at the fourth joint's servo sags when it holds the wrist out, and the health check stopped the arm at 10.1–10.4 V against a 10.5 V limit. This is a hardware fault in that servo's power path. The stop worked as designed, and the limit was not relaxed to get a longer run. The fault-injection and independence runs used a pose where that joint is unloaded.

In the reverse arrangement, where the simulated arm leads and the real arm follows, a 45-second multi-joint motion completed with no faults: the real arm stayed 0.20 s behind, with a joint error of 0.58° at the median once that lag is removed.

Limits and open items

What the result does not cover

  • Two 2-minute runs per condition, one arm, one pose, one motion, one control rate.
  • An effect on the median serial read smaller than about 1 ms would not have been detected.
  • One host. A separate inference machine or a real-time kernel would change the CPU-contention picture.
  • The inference loads in the independence runs were direct calls, without the simulator rendering alongside. The closed-loop runs, which do render, also held 66.67 ms ticks.
  • Diffusion ran 0.9% slower with the arm stack running. That rests on a single baseline run and is unconfirmed.

Still open (7 of 58 issues)

  • hardware The fourth joint's power path. It is the only thing preventing a full-length closed-loop run.
  • hardware The arm's USB device occasionally disconnects.
  • The arm drops an occasional query for an unknown reason. A dropped read now costs one measurement and no delay.
  • JPEG compression at quality 85 moves ACT's output by up to 2.7°, about as much as the quantization that was rejected. The shared-memory path avoids it for +0.5 ms.
  • About 0.2% of renders take 2.6–3.3 ms in every condition; unexplained, and it never caused a missed deadline.
  • Single corrupted health samples can pass the parser, because the arm's health frames carry no checksum.
